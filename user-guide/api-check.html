Checking help text: matlab-api-check¶

The matlab-api-check builder checks the help text of a MATLAB project: that every function, class and public method has a description, that the help describes its inputs, outputs and name-value arguments, and that it has an example; and that every public property has a description. It writes a report, logs each finding, and fails the build when it finds a problem, so it can guard help text in CI.

Running it¶

It is a Sphinx builder; the extension adds it. Run it on the Sphinx project of your docs:

$ sphinx-build -b matlab-api-check docs docs/_build/api-check

It reads the pages like any builder; give it the -d folder of the HTML build (-d docs/_build/doctrees) to avoid reading them twice. (If the two builds use different options, such as -n for HTML only, Sphinx says the configuration changed and reads the pages again; that is harmless.) Then it checks every file the project indexes, whether a page documents it or not, on every run. It writes no pages.

What is checked¶

Every indexed object below the project root, minus matlab_api_check_ignore_patterns (or only the objects of the files matlab_api_check_files selects, see Checking selected files):

  • functions, classes, scripts and apps (.mlapp); a class with the Hidden attribute is not public API and is not checked, nor are its members;

  • public methods: methods without Access = private, protected or an access list, and not Hidden, including static methods and constructors. get./set. methods, converter methods with dotted names and abstract methods (MATLAB’s help shows no text for them) are not checked;

  • public properties of classes: without Access (or, without it, GetAccess) private, protected or an access list, and not Hidden; constant and dependent properties included;

  • public events: without ListenAccess private, protected or an access list, and not Hidden.

Files below private/ and files MATLAB cannot call are checked. Contents.m and the other special files, files that cannot be read and files that cannot be parsed are counted as not checked. The function files of a class folder @X/ whose X.m is a classdef are methods, with the attributes of their signature in a methods block of X.m (Access, Hidden, Static); in an old-style class folder they are functions (old-style classes are not supported, see Documenting MATLAB code).

With matlab_src_sidecar_suffixes, the sidecar docs are checked too: that each is rendered, and that its relative links and images exist.

  • Inputs are the named inputs, except ~, the object of a method that is neither static nor a constructor, and the structure that holds name-value arguments. varargin counts.

  • Outputs are the named outputs; varargout counts. A constructor’s output (the object) does not.

  • Name-value arguments are the opts.Name entries of arguments blocks. Name-value pairs that the code parses itself (varargin with inputParser) are not detected.

  • sidecar-links looks at the sidecar docs as they were rendered, so one that no mat:autosidecar renders gets only a sidecar-documented finding. Links in reST sidecar docs written as `text <path>`_ are not checked.

Comments in arguments blocks count as documentation, although MATLAB’s help does not show them, and neither does the HTML documentation:

function total = totalArea(shapeList, opts)
% TOTALAREA Sum of the areas of several shapes.
%
%   total = shapes.totalArea(shapeList) adds the areas.
%   total = shapes.totalArea(shapeList, Scale=s) multiplies the sum by s.
%
%   The comments in the arguments blocks describe the inputs and the
%   output. matlab-api-check counts them; the documentation does not show
%   them, like MATLAB's help.
%
%   See also shapes.Circle
arguments
    shapeList (1,:) cell  % Shapes that have an area method
    opts.Scale (1,1) double = 1  % Factor applied to the sum
end
arguments (Output)
    total (1,1) double  % The scaled sum of the areas
end
total = opts.Scale * sum(cellfun(@(s) s.area(), shapeList));
checkPositive(total);
end

Section headers¶

A section starts with a help line that begins with one of these labels, in any letter case:

  • inputs: Input, Inputs, Input(s), Input Arguments, Input Parameters, Arguments, Parameters, Params, Required Inputs, Required Arguments, Optional Inputs, Optional Arguments, Optional Parameters;

  • outputs: Output, Outputs, Output(s), Output Arguments, Output Parameters, Returns, Return Values, Return Arguments;

  • name-value: Name-Value Arguments, Name-Value Pairs, Name-Value Pair Arguments, Name-Value Parameters, Name-Value Options (with -, /, a space or nothing between name and value; also with Optional before them), Options, Optional Inputs, Optional Arguments, Optional Parameters. Input Arguments (Name-Value Arguments) counts for inputs and name-value arguments;

  • example: Example, Examples, Example(s), Example 1 (any number), Usage, Example Usage, Usage Example, Usage Examples; also a reST .. rubric:: Example (or Examples, Usage).

The last word of a label may also be singular or plural (Parameter, Return, Option, Name-Value Pair).

The label is followed by one of:

  • : and anything: Inputs: x - data, Options::, Input : x;

  • a short qualifier and a : that ends the line: Inputs (all optional):, Parameters and their meaning:;

  • nothing: INPUTS alone on its line, or Parameters underlined with ---, === or ~~~.

Two cases are not headers: a lowercase label alone on a line right after a line of text (a word of wrapped prose), and a label that is the name of one of the function’s arguments with text after its : (input: the data, the entry of an argument named input). The built-in labels were tuned on the help of 14 open-source MATLAB projects.

matlab_api_check_section_labels sets exactly which labels a section accepts, replacing its built-in ones; the sections you leave out keep theirs. List the headings your project’s help uses:

matlab_api_check_section_labels = {
    "inputs": ["Inputs", "Input"],
    "outputs": ["Outputs", "Output"],
    "name-value": ["Name Value Pairs"],
}

With this, Parameters: or Options: no longer start a section, so help that drifts from the project’s style gets a finding. The entry "<built-in>" adds the built-in labels back, to extend them instead:

matlab_api_check_section_labels = {
    "inputs": ["<built-in>", "Eingaben"],
    "example": ["<built-in>", "Beispiel"],
}

The labels follow the rules above (any case, the same forms, the same two exceptions). [] accepts no label: only arguments-block comments pass the section’s rule. A .. rubric:: Example counts whatever the example labels. The check does not read napoleon_custom_sections: that setting decides how Napoleon formats a section (params_style lists one entry per name, which suits outputs too), not what the section means. A heading in both settings is formatted by Napoleon and counted by the check.

Configuration¶

These settings in conf.py (or -D) configure the check; changing them does not make Sphinx read the pages again (Configuration values):

  • matlab_api_check_rules: the severity of each rule: "error", "warning" or "ignore". The defaults are in the table above (the newer rules property-description, event-description, example and method-example warn). The dictionary is merged over the defaults:

    matlab_api_check_rules = {
    "method-description": "warning",
    "name-value": "ignore",
    "example": "error",
}

  • matlab_api_check_ignore_patterns: objects not to check. Globs with the rules of matlab_src_exclusion_patterns, matched against the path references of files, of methods and properties (+pkg/Cls.m.helper) and of sidecar docs. Use them for generated code, examples and tests:

    matlab_api_check_ignore_patterns = [
    "**/generated/**",
    "examples/**",
    "+pkg/Legacy.m.*",
]

  • matlab_api_check_enabled (default True): False checks nothing; the reports say so. Useful to switch the check off in one configuration without removing the CI step.

  • matlab_api_check_section_labels: the labels each section accepts (above).

  • matlab_api_check_files, matlab_api_check_files_from and matlab_api_check_ignore_unmatched: the files to check; see Checking selected files.

An unknown rule, severity or section is a configuration error.

Checking selected files¶

matlab_api_check_files and matlab_api_check_files_from check only some files, such as the files a pull request changes. The project is indexed and the pages are read as before, so names resolve, links work and the documentation does not change; only the check is narrower, and files that are not selected are not parsed for it. Give the files on the command line, separated by commas:

$ sphinx-build -b matlab-api-check -D matlab_api_check_files=+shapes/Circle.m,utils/ docs docs/_build/api-check

in conf.py, as a list:

matlab_api_check_files = ["+shapes/Circle.m", "utils/", "+pkg/**/*.m"]

or in a text file, one per line (a long list does not fit on a command line):

$ sphinx-build -b matlab-api-check -D matlab_api_check_files_from=changed-files.txt docs docs/_build/api-check

A relative file path is relative to the current folder. The file is read as UTF-8; blank lines and the spaces around a line are dropped, and commas do not separate entries. Its lines are added to matlab_api_check_files.

  • Entries are paths or glob patterns relative to matlab_src_code_project_root, with / and the rules of matlab_src_include_patterns (case-sensitive, ** crosses folders). An entry that ends in / selects every file below that folder.

  • They select files and sidecar docs; a selected classdef file is checked with its methods and properties. A class folder’s method files are files of their own: @Shape/area.m checks that method only, @Shape/Shape.m the class and the methods written in it, and @Shape/ all of them.

  • matlab_api_check_ignore_patterns still apply, and selected Contents.m files are still not checked; the report counts them.

  • [], an empty -D matlab_api_check_files= or an empty file selects nothing: the reports say so, and the build passes. With both settings None, the default, every file is checked.

  • An entry that selects no indexed file or sidecar doc (a typo, a deleted or excluded file, a file that is not MATLAB code, a path relative to another folder) is logged as an ERROR with the reason, listed in both reports, and makes the build exit with status 1, whatever the rule severities, so the check of a file that was asked for cannot pass silently.

  • With matlab_api_check_ignore_unmatched (-D matlab_api_check_ignore_unmatched=1), such entries are still listed in both reports, marked ignored, but they log no error and do not change the exit status.

Both reports count the files selected and the files not selected (not selected) and list the entries that select nothing; api-check.json also lists every entry. See matlab-api-check reports.

In CI, pass the files a change touches, relative to the project root. A list of every changed file holds deleted files and files that are not MATLAB code; ignore those entries rather than filter them. With Git, for a project root src (--relative leaves out files outside it and strips src/):

git diff --name-only --relative=src origin/main... > changed-files.txt
sphinx-build -b matlab-api-check \
    -D matlab_api_check_files_from=changed-files.txt \
    -D matlab_api_check_ignore_unmatched=1 \
    docs docs/_build/api-check

With the project root at the repository root, --relative is not needed. To catch a list relative to the wrong folder, look at the Selected: line, or leave the unmatched entries failing and filter the list (--diff-filter=d leaves out deleted files, pathspecs such as '*.m' other files).

Findings and reports¶

Each finding is logged at the line of the declaration (scripts at line 1, apps without a line), as an ERROR for severity error and a WARNING for warning, with the type mat.api_check:

path/to/file.m:12: ERROR: [sphinxcontrib-matlabdomain] +pkg/f.m (pkg.f): has no inputs section ... [inputs] [mat.api_check]

The output folder gets two reports, written before anything is logged:

  • api-check.txt: one line per finding, then a summary (above);

  • api-check.json: the same for tools, without absolute paths, so it is identical on every system (matlab-api-check reports).

Sphinx’s last line counts the findings among its warnings (“build finished with problems, 1 warning”). A run without errors ends with “The MATLAB API check passed; see …/api-check.txt”.

In CI¶

The exit status is 1 when a finding has severity error or a selection entry selects no file (unless matlab_api_check_ignore_unmatched), and 0 otherwise. With -W, any finding fails the build, like any warning. A CI step:

$ sphinx-build -b matlab-api-check -d docs/_build/doctrees docs docs/_build/api-check

To adopt the check on an existing project, start with the rules that pass, set the others to "warning", and tighten them as the help improves. Keep api-check.json as a build artifact to follow the counts.
