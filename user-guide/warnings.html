Warnings¶

The extension never stops a build because of one bad file: the file gets a warning, and everything else is documented as usual. Each warning has the type mat and a subtype, starts with the path reference of the file, and gives file:line where a line is known. Warnings lists them in a table.

A warning about a directive names the file and line where the directive is written: the page, a file the page includes, a sidecar doc, or help text, as <file>:docstring of <reference>:<line> with the line in the code file. A warning about the text that an auto directive adds around help text, for example a base class that is not documented, names the code file and the line of the declaration: the classdef line, the property line or the function line. A file without such a line, such as a script, is at line 1. A folder has no file, so it is at the auto directive.

Turning warnings off¶

Sphinx’s suppress_warnings turns off warnings by type and subtype:

suppress_warnings = [
    "mat.not_callable",  # one subtype
    "mat.empty_code_file",
]

"mat" turns off every warning of this extension. scmd apidoc reads suppress_warnings from the same conf.py. Warnings about help text that is not valid reStructuredText come from docutils and have the type docutils, which covers every page, not only help text (Help text).

What each warning means¶

mat.config

A matlab_* value in conf.py or -D is not valid, and only another run uses it: an api-check value in an HTML build, an HTML value in a text or LaTeX build, a matlab_apidoc_* value in a build, or a value of the build in scmd apidoc. The warning names the value, what is wrong and the run that uses it; this run goes on without the value. Correct the value, or remove it if no run of the project uses it. The run that uses it stops with a ConfigError instead (Configuration values).

mat.parse_error

A file could not be read (no permission, for example) or parsed, an .mlapp file is not a valid App Designer file (or exceeds the size limits of its reader), a folder could not be listed or entered, or a file name is not valid UTF-8. A file that cannot be read or parsed is still indexed and documented, without content, so links to it work; it is tried again on every build. scmd apidoc lists no file that it cannot read, and gives it one mat.apidoc warning instead of this one. Where the parser found a syntax error, the warning gives its line and column. Two names in one folder that differ only by Unicode form (é as one character and as e and an accent) have the same path reference: the first in the order of the names on disk is documented, the other is left out, and the warning shows both names with escapes ('caf\xe9.m', 'cafe\u0301.m'). Rename one of them.

mat.folder_name

An error, which suppress_warnings does not hide: a folder is named like a file the extension reads (.m, .mlapp, .md, .rst, in any case), so references and output names could take it for a file. The folder and everything in it are not documented; the build goes on. Rename the folder.

mat.encoding

A file is not valid in its encoding: it was decoded with the fallback (Windows ANSI code page or Latin-1), or bytes were replaced. The warning gives the line of the first bad byte. Save the file as UTF-8, or set matlab_src_encoding (Configuration).

mat.invalid_matlab

The file is probably not valid MATLAB: its first line of code says one type and the parser found another (a classdef without its end, function = 1;), a function has a dotted name (function y = pkg.f(x), which MATLAB refuses to run outside a classdef), a classdef names a class other than its file (classdef Other in Shape.m, which MATLAB refuses; letter case counts), or a .m file contains NUL bytes (probably a binary file). It is documented as far as it could be parsed. A dotted function or a misnamed class is documented under its file name.

mat.empty_code_file

The file is empty, or has only blank lines. It is documented as a script. A file with only comments is a help file and does not warn (Help text).

mat.not_callable

MATLAB cannot call the file for matlab_version, so it has no MATLAB name; it is documented and linked by path (Names, references and links). The warning says why (an invalid name such as my-file, a keyword, a subfolder of a class folder, …). Rename or move the file, or suppress the warning if that is intended.

mat.outside_root

A link or Windows junction below the project root points outside it; it is not followed (Configuration).

mat.link_cycle

A link or Windows junction points to the folder it is in or to a folder above it, up to the project root, so following it would list the same files again and again. It is not followed; its folder is documented once, at its own path (Configuration).

mat.ambiguous

A name in a directive, role, “See also” line or auto-link matches several objects, or a reference matches objects in several intersphinx inventories (Linking between projects). The warning lists their path references; use one of them. A name in help text warns once per help text, at the line that first names it. Copies of files (vendored code, symbolic links) are a common cause; exclude them with matlab_src_exclude_patterns. When the copies are intended, matlab_link_shadowed_files_to_chooser_pages links such names to the page that lists the objects and turns the warning off for them (an auto directive still has to name one object). A namespace name where a folder is expected (mat:folder:: shapes) matches each of the namespace’s folders; to document the whole namespace, use mat:namespace or mat:autonamespace and link with :mat:namespace:. mat:autonamespace documents a file that two folders of the namespace have twice, with this warning.

mat.not_found

An auto directive (mat:autofunction and the others) names no object of its kind below the project root (“don’t know which object to document”), so it writes nothing. The warning gives the page and line of the directive. Check the name, the current folder (Names, references and links) and matlab_src_code_project_root. Description directives (mat:function) never read a file and never get it (Documenting MATLAB code). A name in :members: that the object does not have gets it too, and so does a mat:namespace or mat:autonamespace argument that is not the MATLAB name of a namespace of the project (a path, a folder, a class).

mat.directive

A directive got an argument of the wrong kind: mat:folder names a class folder (document the class instead), or mat:autofolder or mat:autonamespace has arguments or a return annotation (a folder or namespace has neither).

It is also the warning for :inherited-members: while matlab_inherited_members is off: the directive documents no inherited member. Set matlab_inherited_members = True in conf.py, or remove the option. When autodoc_default_options sets the option, the build warns once, at start-up.

mat.duplicate

The same object is described twice (add :no-index: to one of the descriptions), or two objects would get the same anchor, so the second cannot be linked. It points at the second description, at the directive a person wrote in a reStructuredText or Markdown file: its own directive, or, for a description generated from help text, the outermost auto directive (a method from :members: points at the mat:autoclass line). “Other instance in” names the other description in the same way, as file:line: the page, an included file, a sidecar doc, or the auto directive. A parallel build (-j) gives the same warnings as a serial one, and an incremental build the same as a fresh one for the pages it reads.

mat.apidoc

scmd apidoc: a file cannot be read (the warning gives the cause, such as Permission denied) and is left out, two output names differ only by letter case, or an output path is longer than Windows allows.

mat.api_check

A finding of the matlab-api-check builder (Checking help text: matlab-api-check), an ERROR or a WARNING depending on the rule’s severity.

Files named Contents.m, slblocks.m and the other special files (Help text) never get mat.invalid_matlab, mat.empty_code_file or mat.not_callable.

When warnings appear¶

  • On every build, for every indexed file: mat.encoding, mat.empty_code_file, mat.not_callable, mat.outside_root, mat.link_cycle, mat.invalid_matlab for NUL bytes, and mat.parse_error for a file or folder that cannot be read.

  • Once per build, for the files that the pages read in that build use: mat.invalid_matlab and mat.parse_error found while parsing. A file that no page uses is not parsed, so it does not get these (the matlab-api-check builder parses every code file, so it reports them all).

Other warnings¶

Messages from docutils and Sphinx themselves, such as an unknown directive option, have no mat type. Fix the directive; suppress_warnings with mat does not hide them.
